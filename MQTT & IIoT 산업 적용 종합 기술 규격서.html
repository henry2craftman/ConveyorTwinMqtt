1. 아키텍처 및 3대 디커플링(Decoupling)

MQTT (Message Queuing Telemetry Transport)는 1999년 Andy Stanford-Clark(IBM)과 Arlen Nipper(Eurotech)가 사막 송유관 모니터링을 위해 위성 통신의 대역폭 한계와 높은 통신비용을 극복하고자 개발한 초경량 이벤트 드리븐 발행/구독(Pub/Sub) 프로토콜입니다.

클라이언트가 직접 통신하지 않고 중앙의 브로커(Broker)를 거침으로써 기존 클라이언트-서버(HTTP) 모델이 지닌 한계를 3가지 차원에서 완벽히 분리(Decoupling)합니다.

공간적 분리 (Space)

발행자와 구독자는 서로의 IP 주소, 포트 번호, 장비 식별자를 알 필요가 없습니다. 오직 메시지의 주소인 Topic만을 기준으로 통신합니다.

시간적 분리 (Time)

메시지 발행 시점에 구독자가 오프라인(배터리 절전, 회선 단절 등) 상태여도 브로커의 세션 유지 기능을 통해 재접속 시 메시지를 수신받을 수 있습니다.

동기화 분리 (Sync)

발행자는 메시지를 브로커로 넘기자마자 자신의 제어 루프로 복귀합니다. 구독자가 처리 중인지 기다리며 대기열이 블로킹되지 않는 비동기 구조입니다.

CONNACK ---------------------| | | |<-- 3. SUBSCRIBE (Topic: plant/T1) -| | |--- 4. SUBACK --------------------->| | | | |-- 5. PUBLISH (plant/T1, "24.5C") ->| | | |== 6. 2. 패킷 구조 및 제어 흐름 (Packet Anatomy)

MQTT는 극소형 MCU 환경(8비트, 수 KB RAM)에서도 동작할 수 있도록 패킷 오버헤드를 극단적으로 줄였습니다. HTTP 요청 헤더가 최소 수백 바이트에서 수 KB에 달하는 반면, MQTT는 고정 헤더 2바이트만으로 동작 가능합니다.

패킷 기본 구조

영역 (Field) 길이 (Size) 포함 정보 및 역할
Fixed Header (고정 헤더) 2 ~ 5 Bytes • 패킷 타입 (1: CONNECT, 3: PUBLISH, 8: SUBSCRIBE 등 총 14~15개 제어 명령)
• 플래그 (DUP, QoS 레벨, RETAIN 플래그)
• 잔여 길이(Remaining Length, 가변 길이 인코딩으로 최대 256MB 표현)
Variable Header (가변 헤더) 가변 (0 ~ N Bytes) • 패킷 식별자 (Packet Identifier / Packet ID - QoS 1, 2 제어용)
• 토픽 이름 (PUBLISH 패킷의 경우 문자열 길이 + 바이트열)
• 프로토콜 버전, Keep Alive 시간 (CONNECT 시)
Payload (페이로드) 가변 (0 ~ 256MB) 실제 전송할 애플리케이션 데이터. 바이너리, 순수 텍스트, 압축 포맷, JSON, Protobuf 등 어떤 포맷이든 원형 그대로 전송 가능 (Format Agnostic).

주요 제어 패킷 목록 (Control Packets)

MQTT 연결 생애 주기 동안 교환되는 주요 패킷들입니다.

연결 수립 및 세션 유지

  • CONNECT / CONNACK: 클라이언트 접속 요청 및 승인/에러 응답
  • PINGREQ / PINGRESP: 하트비트 주기 점검 (TCP 연결 생존 확인)
  • DISCONNECT: 클라이언트의 정상 접속 종료 (LWT 트리거 방지)

데이터 발행 및 구독 제어

  • PUBLISH: 데이터 송신
  • PUBACK, PUBREC, PUBREL, PUBCOMP: QoS 확인 응답
  • SUBSCRIBE / SUBACK: 토픽 등록 및 승인
  • UNSUBSCRIBE / UNSUBACK: 토픽 구독 해제

3. 계층형 토픽(Topic) 구조 및 와일드카드 규칙

토픽은 슬래시(/)를 계층 구분자로 사용하는 대소문자 구분(Case-sensitive) UTF-8 문자열입니다. 브로커는 이 토픽 경로를 기반으로 트리 구조 인덱스를 생성하여 고속 라우팅을 수행합니다.

와일드카드 2종

구분 기호 작동 원리 및 제약 조건 매칭 예시
단일 레벨 + 계층 트리에서 정확히 단 하나의 계층만을 대체합니다. 중간 또는 끝 어느 위치든 올 수 있습니다. ulsan/plant1/+/motor/temperature
→ ulsan/plant1/lineA/motor/temperature (매칭)
→ ulsan/plant1/lineB/motor/temperature (매칭)
× ulsan/plant1/lineA/press/motor/temp (불일치: 2계층 차이)
다중 레벨 # 지정된 위치 이후의 모든 하위 계층을 포괄합니다. 반드시 토픽의 맨 마지막에만 위치해야 합니다. ulsan/plant1/lineA/#
→ ulsan/plant1/lineA/motor/rpm (매칭)
→ ulsan/plant1/lineA/sensor/press/vibration/status (매칭)

시스템 토픽 (`$SYS/`)

대부분의 브로커는 $SYS/로 시작하는 특별한 시스템 토픽을 제공합니다. 일반 클라이언트는 이 토픽으로 발행할 수 없으며(Read-only), 브로커의 CPU 사용량, 연결된 총 클라이언트 수, 초당 인바운드/아웃바운드 메시지 수 등 내부 모니터링 메트릭을 발행합니다.

  • $SYS/broker/version: 브로커 엔진 버전
  • $SYS/broker/clients/connected: 현재 동시 접속 세션 수
  • $SYS/broker/messages/received: 브로커가 수신한 누적 메시지 수
산업 현장 토픽 설계 시 안티패턴(Anti-patterns):
  • 선두 슬래시 지양: /factory/line1처럼 앞에 슬래시를 넣으면 첫 번째 레벨이 빈 문자열("")로 취급되어 트리에 불필요한 공백 노드가 생깁니다. 반드시 factory/line1 형식으로 작성하십시오.
  • 공백 문자 금지: 공백이나 특수기호(*, ?, 공백)는 스크립트 처리 및 디버깅 시 파싱 에러를 유발합니다.

4. QoS(Quality of Service) 및 4-Way 핸드셰이크

MQTT는 네트워크의 전송 신뢰도와 대역폭 사용량 간의 타협점을 맞출 수 있도록 3단계의 QoS 수준을 제공합니다.

QoS 0 : At most once

최대 1회 전송 (Fire and Forget)
확인 응답(ACK)이 없으며 TCP 연결이 끊기면 데이터는 영구 유실됩니다. 메시지 패킷 ID가 할당되지 않습니다.

용도: 100ms 단위의 지속적인 진동/온도 센서 스트리밍.

QoS 1 : At least once

최소 1회 전송 (ACK 보장)
수신 측에서 PUBACK 패킷을 회신할 때까지 송신 측이 메시지를 재전송합니다. 네트워크 지연 발생 시 중복 수신이 발생할 수 있습니다.

용도: 설비 가동/정지 상태 변경 이벤트, 알람.

QoS 2 : Exactly once

정확히 1회 전송 (중복 방지)
두 번의 왕복 교환(4-way 핸드셰이크)을 거쳐 수신 측에 중복 전송이나 유실 없이 정확히 한 번만 전달됩니다. 오버헤드가 가장 큽니다.

용도: PLC 긴급 비상정지 지시, 금융 거래, 제품 생산 카운팅.

QoS 2 세부 패킷 핸드셰이크 흐름

Sender (Client/Broker) Receiver (Broker/Client) | | [Step 1] --- PUBLISH (Packet ID: 101, QoS 2) ----->| (메시지 임시 저장, ID 등록) | | [Step 2] <-- PUBREC (Packet ID: 101) --------------| (수신 완료 응답 - "Publish Received") (ID 락, 재전송 중지) | | [Step 3] --- PUBREL (Packet ID: 101) ------------->| (릴리즈 요청 - "Publish Release") | | (컨슈머에게 데이터 방출, ID 해제) [Step 4] <-- PUBCOMP (Packet ID: 101) -------------| (완료 확인 - "Publish Complete") (보관 중인 메시지 삭제)| |

5. 통신 신뢰성 엔진: LWT, Retained, PING

1) 유언 메시지 (LWT, Last Will and Testament)

IoT 설비는 배터리 방전, 현장 케이블 단선, OS 크래시 등으로 인해 명시적인 종료 신호(DISCONNECT)를 보내지 못하고 전원이 꺼질 수 있습니다. LWT는 이러한 비정상 단절을 즉시 감지하는 장치입니다.

  • 등록: 클라이언트가 CONNECT 패킷을 브로커에 보낼 때 유언 토픽, 유언 내용(Payload), QoS, Retain 플래그를 미리 심어둡니다.
  • 트리거: 정상 DISCONNECT 수신 없이 TCP 연결이 강제로 끊어지면, 브로커가 등록된 유언 메시지를 해당 토픽으로 대신 발행합니다.
  • 실무 패턴: 접속 시 factory/line1/status 토픽에 "ONLINE"(Retained)을 발행하고, LWT에는 "OFFLINE"(Retained)을 설정합니다. 이렇게 하면 설비 장애 발생 즉시 모든 관제 시스템이 이상을 인지합니다.

2) 보관 메시지 (Retained Message)

일반적으로 브로커는 메시지를 구독자들에게 배달한 직후 즉시 메모리에서 제거합니다. 그러나 RETAIN = 1 플래그를 달아 메시지를 보내면, 브로커는 해당 토픽의 가장 최신 메시지 1개를 디스크 또는 메모리에 지속 보관합니다.

  • 신규 구독자가 뒤늦게 해당 토픽을 SUBSCRIBE하는 순간, 다음 센서 데이터가 측정될 때까지 대기할 필요 없이 저장되어 있던 마지막 상태값을 즉각 전달받습니다.
  • 삭제 방법: 해당 토픽으로 페이로드가 빈 값(0 Byte, null)인 Retained 메시지를 1회 발행하면 브로커 캐시에서 완전히 소거됩니다.

3) Keep Alive 및 PING 매커니즘

TCP 프로토콜 자체의 Keep-Alive는 주기가 매우 길어 수 시간 동안 끊김을 인지하지 못할 수 있습니다. MQTT는 애플리케이션 계층에서 Keep Alive 타이머(초 단위)를 설정합니다.

  • 클라이언트는 데이터 통신이 없더라도 약속된 시간(예: 60초) 내에 최소 1회 이상 패킷을 보내야 합니다. 보낼 데이터가 없다면 2바이트 크기의 PINGREQ를 발행합니다.
  • 브로커는 PINGRESP로 회신합니다. 설정된 Keep Alive 시간의 1.5배(예: 90초) 동안 아무 패킷도 도달하지 않으면 브로커는 클라이언트가 사망한 것으로 간주하고 소켓을 강제 차단한 뒤 LWT를 실행합니다.

6. MQTT v3.1.1 vs MQTT v5.0 심층 비교

8. OT 레거시 프로토콜 연계 (Bridge & Gateway)

제조 현장에는 이미 구축된 수천 대의 PLC와 CNC 머신이 존재하며, 대부분 인터넷 연결이나 MQTT를 직접 지원하지 않는 산업용 필드버스 프로토콜을 사용합니다. 따라서 엣지 게이트웨이(Edge Gateway)를 통해 이들을 수집하고 MQTT로 변환(Bridging)하는 파이프라인이 산업 적용의 제1관문입니다.

Modbus RTU / TCP → MQTT

  • 특징: 16비트 레지스터(Holding, Input) 및 코일(Coil) 번지 기반의 데이터 맵. 단위나 메타데이터가 전혀 없음.
  • 변환 전략: 엣지 게이트웨이가 Modbus Master로서 수백 밀리초 주기로 슬레이브 PLC를 폴링한 뒤, 수집된 정수 값을 스케일링(예: VAL / 10.0)하여 엔지니어링 단위(℃, bar 등)가 포함된 JSON MQTT 메시지로 조립.

OPC UA → MQTT

  • 특징: 복잡한 객체 지향 정보 모델, 태그 메타데이터, 내장 보안(암호화/전자서명)을 갖춘 현대 스마트 공장의 사실상 표준.
  • 변환 전략: 게이트웨이가 OPC UA Client로서 서버의 노드(Node ID) 변경 이벤트를 구독(Subscription & Monitored Items)하고, 변경 발생 시에만 MQTT로 압축 발행하는 Report-by-Exception 전략 수립.

엣지 컴퓨팅 전처리 아키텍처

공장 설비의 고주파 센서(진동 가속도계, 고전압 전류 센서)는 초당 1,000Hz ~ 20,000Hz의 데이터를 생산합니다. 이 원시(Raw) 데이터를 전부 MQTT 브로커로 전송하면 공장 내부 네트워크와 클라우드가 마비됩니다.

현장 필수 엣지 전처리 기법:
  • Deadband (불감대) 필터링: 이전 측정값 대비 변화폭이 설정된 임계치(예: ±1.5%) 미만이면 발행을 생략하여 유휴 트래픽을 90% 이상 감축.
  • 엣지 통계 요약: 1초 동안 10,000번 수집한 센서 값에서 RMS(실효값), Peak-to-Peak, Kurtosis(첨도), 평균만을 계산하여 1초에 1회 요약 패킷으로 발행.
  • 엣지 FFT(고속 푸리에 변환): 진동 데이터를 현장에서 즉시 주파수 스펙트럼으로 변환하여 베어링 결함 주파수 대역의 에너지만 MQTT로 전송.

9. 산업용 표준 페이로드 규격: Sparkplug B

일반 MQTT의 치명적인 약점은 "페이로드 포맷의 자유로움"입니다. A사 설비는 {"t": 25.1}로, B사 설비는 {"TEMP_VAL": "25.1 C"}로 발행하면 전체 SCADA 시스템 통합 시 수백 개의 맞춤 파서를 짜야 합니다. Sparkplug B (Eclipse Tahu)는 IIoT 환경에서 플러그 앤 플레이(Plug-and-Play) 상호운용성을 제공하기 위해 MQTT 위에 정립된 표준 프로토콜 규격입니다.

1) 엄격한 표준 토픽 네임스페이스

Sparkplug B는 모든 토픽을 다음 5단계의 단일 구조로 고정합니다.

spBv1.0 / {Group_ID} / {Message_Type} / {Edge_Node_ID} / [{Device_ID}]
  • spBv1.0: 스파크플러그 버전 명시
  • Group_ID: 공장 구역, 라인, 플랜트 이름 (예: AssemblyLineA)
  • Message_Type: 노드 및 장비 상태 머신 메시지 유형 (12종)
  • Edge_Node_ID: 물리 엣지 게이트웨이 또는 IPC 식별자 (예: Gateway01)
  • Device_ID: (선택) 게이트웨이에 종속된 세부 센서/PLC ID (예: PLC_Mitsubishi_FX5U)

2) 노드 생애 주기 제어 (State Machine Messages)

메시지 타입 명칭 및 시점 내용 및 역할
NBIRTH Node Birth (노드 탄생) 엣지 노드가 브로커에 접속 완료된 즉시 발행. 노드가 보유한 모든 태그 목록, 데이터 타입, 초기값을 선언 (Birth Certificate).
DBIRTH Device Birth (장비 탄생) 노드에 연결된 하위 장비(PLC 등)가 활성화될 때 장비의 태그 메타데이터와 초기값을 공표.
NDATA / DDATA Data (데이터 변경 보고) 값이 변경된 태그만 선별하여 전송 (Report-by-Exception). 태그 이름 대신 압축된 Alias(정수 ID)를 사용하여 패킷 크기 극소화.
NCMD / DCMD Command (제어 명령) 상위 SCADA/MES가 현장 엣지 노드 또는 장비에 파라미터 변경, 리부팅, 태그 재선언(Rebirth) 등을 지시.
NDEATH / DDEATH Death (노드 사망) 브로커의 LWT 메커니즘과 연동되어 엣지 노드가 비정상 통신 단절될 때 브로커가 즉각 대행 발행.

3) Google Protocol Buffers (Protobuf) 인코딩

Sparkplug B는 텍스트 기반 JSON을 쓰지 않고 구글의 Protobuf 이진 직렬화를 강제합니다. 동일한 100개의 공정 태그를 전송할 때 JSON 대비 데이터 페이로드 크기를 80~90% 이상 절감하며, 스키마 기반 타입 검증을 보장합니다.

10. 엔터프라이즈 데이터 파이프라인 아키텍처

MQTT 브로커는 **데이터를 중계(Transit)하는 엔진**이지, 수백 테라바이트를 저장하고 분석하는 데이터베이스가 아닙니다. 산업 환경에서는 브로커 후단에 데이터 엔지니어링 파이프라인을 구축해야 합니다.

[ Field OT Tier ] [ Edge / Gateway ] [ Broker Tier ] [ Enterprise Data Tier ] +---------------+ +----------------+ +------------------+ +-----------------------+ | Motors, PLCs | --Modbus-> Node-RED / | --MQTT-> | EMQX / HiveMQ | =====> | InfluxDB / Timescale | | Robots, CNCs | --OPC UA-> ThingsBoard | (TLS) | (Broker Cluster) | (Sink) | (시계열 센서 데이터 보관)| +---------------+ +----------------+ +--------+---------+ +-----------+-----------+ | | | (Rule Engine) v +====> Apache Kafka ====> [ Grafana 관제 대시보드 ] (대용량 버퍼) [ MES / AI 이상감지 서빙 ]

파이프라인 구축 패턴 3선

  • 패턴 A: 브로커 내장 Rule Engine 직접 싱크 (EMQX 등): 추가 브릿지 서버 없이 브로커 자체 SQL 엔진(SELECT payload.temp FROM "factory/+" WHERE payload.temp > 80)을 이용해 InfluxDB, PostgreSQL 등으로 밀리초 단위 직접 저장.
  • 패턴 B: Telegraf MQTT Consumer 데몬 활용: 오픈소스 에이전트인 Telegraf가 MQTT 브로커를 상시 구독하여 데이터를 파싱/배칭(Batching)한 뒤 InfluxDB에 초당 수천 건 단위로 벌크 인서트.
  • 패턴 C: Kafka 브릿지를 통한 빅데이터 연계: 공장 수십 곳의 데이터가 초당 수십만 건 이상 몰릴 때, MQTT 브로커 뒷단에 Kafka 클러스터를 두어 배압(Backpressure)을 흡수하고, Flink/Spark 스트리밍 엔진으로 실시간 머신러닝 이상 탐지 수행.

11. 고가용성(HA) 클러스터링 및 오프라인 복원력

브로커 클러스터링 및 무중단 이중화

단일 브로커(Single Point of Failure) 장애 시 공장 전체 라인이 멈출 수 있습니다. 엔터프라이즈 환경에서는 3대 이상의 브로커 노드를 클러스터링합니다.

  • 분산 세션 및 라우팅 테이블 동기화: EMQX(Mnesia/Ekka 라이브러리 기반), HiveMQ 등의 브로커는 노드 간 분산 라우팅 트리를 공유합니다. 어떤 브로커 노드에 접속하든 다른 노드에 접속한 구독자에게 즉각 메시지가 라우팅됩니다.
  • L4 로드 밸런싱 (HAProxy / NGINX): 클라이언트 전면에 로드 밸런서를 배치하고 Proxy Protocol v2를 활성화하여 로드 밸런서 뒷단에서도 클라이언트의 실제 원본 IP를 추적할 수 있도록 구성합니다.

로컬 버퍼링: Store-and-Forward (오프라인 캐싱)

공장과 클라우드 데이터센터 간의 외부 인터넷망(WAN)은 번개, 지중 케이블 단선, ISP 장애 등으로 언제든 단절될 수 있습니다.

Store-and-Forward 동작 프로세스:
  1. 공장 현장 내부에 엣지 브로커(또는 엣지 게이트웨이 캐시 엔진)를 설치합니다.
  2. 설비들은 외부 클라우드가 아닌 내부 엣지 브로커로 데이터를 초당 전송합니다 (정상 통신 지속).
  3. 엣지 브로커는 클라우드 상위 브로커로 MQTT 브릿지(Bridge) 연결을 유지합니다.
  4. 외부 WAN망이 차단되면, 브릿지 연결 실패를 감지하고 수집되는 모든 시계열 데이터를 로컬 NVMe/SSD SQLite/RocksDB 버퍼에 FIFO 순서로 압축 저장(Store)합니다.
  5. 인터넷망이 복구되면 상위 브로커와 핸드셰이크 후, 적체된 데이터를 타임스탬프 순서대로 순차 전송(Forward)하여 데이터 영구 결손(Gap)을 방지합니다.

12. OT 사이버 보안: mTLS, ACL, ISA-95 준수

1) 전송 계층 암호화 및 mTLS (상호 인증)

공장 네트워크에서는 단순 ID/PW 방식은 탈취 위험이 큽니다. 반드시 mTLS (mutual TLS, 양방향 인증)를 적용해야 합니다.

  • 포트 분리: 기본 평문 1883 포트는 전면 폐쇄하고, TLS 적용 포트 8883 및 WSS(보안 웹소켓) 8084만 개방합니다.
  • 클라이언트 인증서: 브로커만 인증서를 가지는 일반 HTTPS와 달리, 모든 PLC와 게이트웨이 기기마다 자체 사설 CA(Certificate Authority)에서 서명 발급한 개별 X.509 클라이언트 인증서와 개인키를 설치하여 하드웨어 단위로 신원을 확인합니다.

2) 세분화된 토픽 기반 ACL (Access Control List)

인증을 통과했더라도 모든 토픽에 접근해서는 안 됩니다. 최소 권한 원칙(Principle of Least Privilege)에 따라 읽기(Sub)와 쓰기(Pub) 권한을 엄격히 통제합니다. 

# ACL 정책 설정 예시 (Mosquitto/EMQX 규격)
# 라인1 로봇 제어 컨트롤러: 제어 명령 수신만 가능, 센서 데이터 발행만 가능
user robot_arm_controller_01
topic read factory/line1/robot/command
topic write factory/line1/robot/telemetry

# 관제실 관리자 계정: 전체 라인 모니터링 구독 가능, 긴급 제어 명령 발행 가능
user supervisory_admin
topic read factory/#
topic write factory/+/+/emergency_stop

# 게스트/분석 시스템: 모든 텔레메트리 읽기만 가능 (제어 토픽 쓰기 절대 차단)
user data_scientist
topic read factory/+/+/telemetry

3) ISA-95 / Purdue 모델(제어망 5계층)과의 통합

보안 상 공장 내부 제어망(Level 0~2: 센서/PLC)은 인터넷(외부 클라우드, Level 4~5)과 직접 소통할 수 없습니다. 따라서 산업용 비무장지대(IDMZ, Industrial DMZ - Level 3.5)에 MQTT 브로커를 배치하고, 외부망 및 내부망과의 트래픽을 단방향 방화벽으로 철저히 분리 통제해야 합니다.

2) Python 3 기반 산업용 Publisher (paho-mqtt v2, MQTT v5 규격)

LWT 설정, User Properties 주입, QoS 1 안정 전송이 구현된 실무형 센서 시뮬레이터 예제입니다.

import time
import json
import random
from paho.mqtt import client as mqtt_client
from paho.mqtt.enums import MQTTProtocolVersion
from paho.mqtt.properties import Properties
from paho.mqtt.packettypes import PacketTypes

BROKER = "localhost"
PORT = 1883
CLIENT_ID = "edge-gateway-line1"
STATUS_TOPIC = "factory/line1/status"
DATA_TOPIC = "factory/line1/press/telemetry"

def on_connect(client, userdata, flags, rc, properties=None):
    if rc == 0:
        print("[Connected] 브로커 접속 성공")
        # 온라인 상태 알림 (Retained = True)
        client.publish(STATUS_TOPIC, payload="ONLINE", qos=1, retain=True)
    else:
        print(f"[Failed] 접속 실패 에러 코드: {rc}")

# 1. 클라이언트 인스턴스 생성 (MQTT v5 지정)
client = mqtt_client.Client(
    callback_api_version=mqtt_client.CallbackAPIVersion.VERSION2,
    client_id=CLIENT_ID,
    protocol=MQTTProtocolVersion.MQTTv5
)
client.on_connect = on_connect

# 2. 비정상 단절 대비 LWT (유언 메시지) 등록
client.will_set(topic=STATUS_TOPIC, payload="OFFLINE_ABNORMAL", qos=1, retain=True)

# 3. 브로커 연결
client.connect(BROKER, PORT, keepalive=30)
client.loop_start()

try:
    while True:
        # 센서 데이터 수집 모사
        sensor_data = {
            "pressure_bar": round(random.uniform(4.5, 6.2), 2),
            "oil_temp_c": round(random.uniform(55.0, 78.5), 1),
            "cycle_count": 1042
        }
        
        # MQTT v5 User Properties (메타데이터 주입)
        props = Properties(PacketTypes.PUBLISH)
        props.UserProperty = [("site", "ulsan"), ("sensor_vendor", "siemens")]

        # QoS 1 전송
        client.publish(
            DATA_TOPIC,
            payload=json.dumps(sensor_data),
            qos=1,
            properties=props
        )
        print(f"[Published] 데이터 송신: {sensor_data}")
        time.sleep(1)

except KeyboardInterrupt:
    print("[Shutdown] 정상 종료 시퀀스 실행")
    # 정상 종료 시 OFFLINE 상태로 명시 변경 후 정상 disconnect
    client.publish(STATUS_TOPIC, payload="OFFLINE_NORMAL", qos=1, retain=True)
    client.disconnect()
    client.loop_stop()

14. 산업 적용 교육생 실무 훈련 커리큘럼 (5단계 로드맵)

단순 문법 학습에 그치지 않고, 교육생이 실제 제조/플랜트 현장에 투입되어 통신망을 구축하고 트러블슈팅할 수 있도록 구성한 현업 중심 실무 훈련 체계입니다.

모듈 주요 학습 내용 실습 과제 및 검증 기준
Level 1
프로토콜 기초		 • MQTT 기본 철학 및 Pub/Sub 메커니즘
• Wireshark 패킷 분석 (CONNECT, PING, QoS 핸드셰이크)
• 계층형 토픽 네임스페이스 수립 및 와일드카드 실습 		Wireshark로 QoS 0, 1, 2 패킷을 직접 캡처하고 왕복 단계별 패킷 차이점을 설명서로 제출
Level 2
OT 게이트웨이 연동		 • Modbus RTU/TCP 레지스터 맵 독해 및 데이터 폴링
• Node-RED를 활용한 Modbus-to-MQTT 프로토콜 변환
• 데드밴드(Deadband) 및 엣지 연산 전처리 로직 구현 		가상 Modbus PLC 시뮬레이터의 온도/압력 레지스터를 읽어 정규화된 JSON MQTT로 변환 전송
Level 3
스마트 공장 표준화		 • Sparkplug B 아키텍처 및 Protobuf 직렬화
• NBIRTH, NDATA, NDEATH 상태 머신 생애주기 코딩
• 토픽 앨리어스(Topic Alias) 및 페이로드 압축 기법 		Sparkplug B 라이브러리를 통해 엣지 노드가 단절되었을 때 SCADA 관제에 NDEATH가 뜨도록 구현
Level 4
엔터프라이즈 파이프라인		 • InfluxDB 시계열 데이터베이스 스키마 설계
• Telegraf / EMQX Rule Engine 데이터 싱크 파이프라인
• Grafana 기반 실시간 제조 라인 이상 모니터링 패널 제작 		초당 100건 이상의 센서 데이터를 유실 없이 InfluxDB에 적재하고 Grafana 알람(Alert) 구축
Level 5
엔터프라이즈 보안 및 장애 대응		 • OpenSSL 사설 CA 구축 및 mTLS 클라이언트 인증서 발급
• 라인별 제어 토픽 쓰기 방지 ACL 정책 구성
• 네트워크 단절 모사(Store-and-Forward 로컬 캐싱 복구) 		비인가 장비 차단 테스트 통과 및 랜선을 물리적으로 뽑았다 꽂았을 때 과거 데이터 무손실 복구 시연
